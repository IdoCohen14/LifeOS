# חבילת הכנה לשרת Linux קבוע

החבילה מכינה את הקוד לאירוח; היא אינה אתר שפורסם ואינה אישור לפתיחת חשבון, חיוב, DNS, פתיחת פורטים, שינוי Google או העברת מידע אישי. לא הותקן דבר בענן. תקציב חודשי: $0. בחירת ספק וזמינות מסלול חינם ייבדקו בנפרד לפני פרסום.

## מבנה ההתקנה המיועד

- קוד: `/opt/lifeos`; משתמש שירות ללא הרשאות ניהול: `lifeos`.
- Python virtualenv: `/opt/lifeos/.venv`, עם תלויות `services/api/requirements.lock.txt`.
- Node המתאים לגרסת Next שב־`apps/web/package-lock.json`, בנתיב `/usr/bin/node`; התקנה באמצעות `npm ci` בתוך `apps/web`.
- מאגר SQLite, מסמכים ומפתחות פרטיים: `/var/lib/lifeos`, בבעלות `lifeos`, תיקייה `0700`. המידע חייב להיות בדיסק קבוע, מחוץ לקוד ולתיקיית סנכרון.
- הגדרות: `/etc/lifeos`, בבעלות `lifeos`, תיקייה `0700`. קובצי סודות `0600`.
- שירותי API ואתר מאזינים רק ל־`127.0.0.1:8765/3000`. רק Caddy מיועד לסיום HTTPS, בשלב פרסום נפרד.

## הכנה עתידית לאחר אישור סביבת היעד

אלו הוראות למפעיל בסביבת Linux המיועדת; לא הורצו על התקנה אישית או בשרת חיצוני. יש להכין מראש משתמש ותיקיות בבעלות המתאימה, Python ותלויות ו־Node, בלי להעתיק מאגר אישי או קובצי `.env` קיימים.

הפקודה הבאה, כמשתמש `lifeos`, דורשת תיקיות נתונים והגדרות ריקות. מחליפים את כתובת הדוגמה בכתובת HTTPS שאושרה:

```sh
/opt/lifeos/.venv/bin/python /opt/lifeos/scripts/server_manage.py init \
  --data-dir /var/lib/lifeos --config-dir /etc/lifeos \
  --origin https://lifeos.example
```

הכלי מייצר מפתח פנימי אקראי ומפתח הצפנה מקומי ל־Linux, מבצע מיגרציות Alembic ויוצר מאגר ללא חשבונות. הוא אינו מדפיס מפתחות ואינו דורס התקנה קיימת. `runtime.env` משותף לשרת, לאתר ולתהליך הסנכרון. `edge.env` מכיל רק כתובת ופורט, ללא מפתח ה־API. לא מפעילים מחדש `init` לצורך עדכון; אם ההכנה נקטעה, בודקים את הקבצים הפרטיים ומשלימים מיגרציה לאחר עצירת השירותים. אין למחוק אוטומטית נתונים כדי לנסות שוב.

בונים את האתר מתוך `apps/web` עם `LIFEOS_BUILD_DIR=.next-server-release NEXT_TELEMETRY_DISABLED=1 npm run build`. אין להכניס סודות למשתני `NEXT_PUBLIC_*`. מעתיקים את `lifeos*.service` ואת `lifeos.target` ל־`/etc/systemd/system` עם הרשאות `0644`. שירות האתחול מבצע מיגרציה לפני שאר השירותים. אין צורך במודל מקומי: בפרופיל השרת המודל מושבת, ועזרה מובנית ותכנון מבוסס כללים נשארים זמינים.

לפני שדרוג: עוצרים את `lifeos.target`, מגבים את כל תיקיית הנתונים ואת ההגדרות באופן פרטי, מחליפים קוד/תלויות/בנייה ורק אז מפעילים מחדש את היעד. לא מפעילים מיגרציה במקביל לתהליך פעיל. אין לבצע downgrade של בסיס נתונים על סמך החלפת קוד בלבד. מפתח `provider.key` הוא חלק הכרחי מגיבוי הנתונים. גיבוי באותו דיסק אינו הגנה מאובדן הדיסק; יעד גיבוי חיצוני דורש החלטה ואישור נפרדים.

## גבול הפרסום

### פיילוט סגור

להכנה מקומית נבחרה אפשרות `scripts/server_manage.py init --pilot` עם אותם דגלי origin/data/config. היא מייצרת LIFEOS_PILOT_OWNER_ID בקובץ הפרטי. לפני עליית API יש לטעון את runtime.env לפרוצס התפעול ולהריץ `scripts/provision_pilot_owner.py --login <owner>` עם סיסמה מוסתרת; אפשרות --password-stdin מיועדת לאוטומציה פרטית בלי הדפסת סודות. לא משתמשים בסיסמה בארגומנט. הכלי פועל offline ובמאגר ריק בלבד ומסרב ליצור שוב אחרי הקמה/מחיקה. ההרשמה נשארת חסומה והגישה/רקע מוגבלים לבעלים. אין להגדיר זאת בהתקנה האישית ללא אישור הפעלה נפרד. הסמן .pilot-owner-provisioned נשמר כדי למנוע יצירה חוזרת; אין להסירו אוטומטית.

התקנת Caddy הרשמית וקובץ `Caddyfile` מיועדים לשלב פרסום בלבד. ה־drop-in בשם `caddy-lifeos.conf` מיועד ל־`/etc/systemd/system/caddy.service.d/lifeos.conf`; קובץ האתר מיועד ל־`/etc/caddy/Caddyfile`. אין להפעיל אותו, לפתוח 80/443 או לבצע בקשת תעודה במסגרת ההכנה המקומית. אין לחשוף את פורטי האפליקציה. Caddy מקבל רק `edge.env`; אין להעביר אליו את `runtime.env`.

יש להתאים בעתיד את כתובת החזרה ב־Google ל־`https://<approved-host>/api/accounts/oauth/callback` ולקבל הסכמה לחיבורים. אין להעתיק סודות DPAPI של Windows ל־Linux. חבילת השרת מתחילה ריקה. מחיקת חשבון ושחזור גישה במפתח אישי מומשו מקומית בסכמה0044. מדיניות גיבוי שרת ומניעת החזרת חשבונות שנמחקו לאחר שחזור עדיין דורשות החלטה לפני הרשמה לציבור.

## מה אומת ומה לא

אומתו בנתוני דמה: אתחול בסכמה0044, מיגרציה ושימור מידע/מפתחות, הפרדת שני חשבונות, Secure cookies וכתובת HTTPS קבועה, השבתת מודל, והפעלה מחדש. בפועל ב־Ubuntu עברו הצפנת FE1 והרשאות0600/0700, בניית Next והפעלת API/אתר על loopback, שחזור גישה וביטול התחברות, מחיקת חשבון מדומה ושמירת השני. Caddy adapt --validate עבר ללא פתיחת מאזינים וללא בקשת תעודה.

טרם בוצעו: הפעלת יחידות systemd המותקנות ביעד, אתחול VM, הנפקת TLS ציבורית, OAuth אמיתי, דיסק ספק ושחזור שרת מלא או רגרסיה רחבה. בדיקת systemd המוקדמת קראה תבניות אך הסתיימה1בגלל היעדר קובצי הפעלה בנתיבי ההתקנה; אינה בדיקת שירותים שעברה. פירוט ב־docs/TESTING_BACKLOG_HE.md וב־ACCOUNT_LIFECYCLE_CHECKPOINT_2026_10_30.md.

מקורות תחביר: [משתני סביבה ב־Caddy](https://caddyserver.com/docs/caddyfile/concepts), [systemd.service](https://www.freedesktop.org/software/systemd/man/252/systemd.service.html). המקורות אינם התחייבות לאירוח חינם.

אם אישור מחיקה של משתמש הסתיים ב־cleanup_pending: החשבון נשאר חסום. לאחר עצירת LifeOS, מפעיל רשאי להשלים רק מחיקה שכבר אושרה באמצעות scripts/finish_account_deletion.py עם --data-dir מוחלט, --account-id מזהה החשבון ו־--confirm. הכלי אינו מאשר מחיקה חדשה של חשבון פעיל. מפתח שחזור אינו כלול בייצוא הלוגי של החשבון; אין להבטיח ששחזור ארכיון מחליף אמצעי גישה.
